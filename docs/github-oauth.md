# GitHub sign-in deployment

The static Studio uses GitHub App user authorization with authorization code + S256 PKCE. GitHub currently requires a client secret during exchange even with PKCE: https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app

The isolated `auth/github-exchange.mjs` service is a portable Fetch API handler. It can run as a Cloudflare Worker using `auth/wrangler.toml`; it has no graph dependencies or npm runtime dependencies. GitHub Pages continues serving the application.

1. Register a **new GitHub App** in GitHub developer settings. Set its homepage to your Studio URL and its user authorization callback to the exact Studio URL, including the trailing slash (for this deployment: `https://mnichols08.github.io/constellation/`). Disable webhooks unless needed separately. Do not enable Device Flow. Keep expiring user tokens enabled.
2. Use public account data with no account write permissions and no repository write permissions. Leave optional permissions unset; GitHub's mandatory repository Metadata permission is read-only. Do not request broad OAuth `repo` scope. Test public profile and pinnedItems GraphQL access using a user authorization token before rollout; only add a documented read permission if GitHub requires it for your chosen data.
3. Set `GITHUB_CLIENT_ID`, `GITHUB_REDIRECT_URI`, and `STUDIO_ORIGIN` in the service environment. The origin is only `https://mnichols08.github.io`, without a path. Keep the callback exact and fixed server-side.
4. Store `GITHUB_CLIENT_SECRET` in the deployment host's secret store. For a Worker, from `auth/`, use your installed Wrangler CLI: `wrangler secret put GITHUB_CLIENT_SECRET`, then `wrangler deploy`. Apply the host's rate limit to the exchange endpoint. Do not log request/response bodies, authorization codes or tokens. No secret goes in the repository, Pages variables or browser JavaScript.
5. Fill the public `constellation-oauth-client` and `constellation-oauth-exchange` meta values in `index.html` with the client ID and HTTPS service URL. Deploy the static site normally. Empty values leave public exploration usable and explain that sign-in is not configured.
6. Verify **Continue with GitHub** against the real app: approve and deny consent, test a mismatched/expired callback, verify username/avatar, public repositories and pins, and sign out. The automated tests simulate GitHub; live consent cannot be verified until the owner registers and deploys the app/service.

A 32-byte random state and 32-byte verifier are stored in sessionStorage for at most ten minutes and consumed once. The callback URL is cleared before exchanging. Only the code and verifier go to the service. Its fixed-origin CORS response contains only the access token; refresh tokens and upstream errors are discarded. Access tokens remain in page memory and are confined to `https://api.github.com` with redirects rejected. Reload requires authorization again; saved local designs remain available. Sign out clears memory and cancels pending authorization, but does not revoke the GitHub App grant. Users can revoke that grant in GitHub settings.

The browser's draft/preset/config/scene/export paths do not receive credentials. Local preview keeps `.env` / `GH_TOKEN`, CLI and Actions keep their existing token support. A collapsed **Advanced local development** token fallback exists only on localhost; it is absent from hosted onboarding. For local OAuth testing, register a separate localhost callback/app and configure matching public meta values and broker environment.

Public GitHub request caching, its freshness window, refresh behavior and authenticated-response storage policy are described in [GitHub request caching](github-data-cache.md).
